# 🟥 Focus

Software engineering is an exercise in managing deep abstraction. That needs long, uninterrupted blocks of concentration. Focus is the art of saying no.

Focus is not working longer. It is removing the interruptions that keep hard work from happening. Collaboration stays. The team agrees when someone is available for it.

---

## 🎯 Single-tasking

A switch costs more than the minute spent answering. The engineer has to rebuild the model: the rule, the assumptions, and the next edit. Repeated switches leave more unfinished work, more missed edge cases, and weaker estimates.

Keep at most three tasks active. The rest wait on a queue. Each active task carries its outcome, its current state, the next step, what blocks it, and when it is done.

A new request does not join the active set on arrival. Ask:

* Is it more important than the current work?
* Must it happen now?
* If it becomes active, which task pauses?
* Who needs to know?

Ownership here means continuity. Other people can review and decide. The engineer keeps one thread intact until it is finished or explicitly paused.

---

## 🧱 Deep work blocks

Deep work is a protected stretch on one hard task: learning a mechanism, implementing it, tracing a production defect, refactoring a knot, weighing a trade-off, or proving a small idea. The aim for most roles is 2–4 hours in a day that can hold them. A day of incidents and reviews may hold less. The number is not a quota to grind toward.

Name the block before opening the editor:

1. **Outcome.** What will be true when the block ends?
2. **Boundary.** Which part of the system is in play?
3. **First step.** What is the first concrete action?
4. **Interruptions.** Which events may break the block?

"Work on payments" is not an outcome. "Find the missing status check and land the smallest tested change" is.

---

## 🔕 Environmental control

During the block, chat, phone, mail, and unrelated tabs stay quiet. Ordinary requests wait until the block ends. The engineer is not unreachable. Availability has a default and an exception.

Name the exceptions before the block starts. A production failure that harms customers, or a security incident, can break it. A status question and an optional review wait. The list belongs to the team. Urgency is not whatever the latest badge feels like.

Make the block visible: until when, where ordinary questions go, and which channel is for a real incident. One person going silent while everyone else expects an instant reply will not last. The team needs collaboration windows, a stated response time, and a known incident path.

Async is the default for status, review comments, documentation questions, and design notes that can wait. A message carries the context, the problem, what was already checked, the decision needed, and when it is needed. Talk live when the problem has several readings, several people must decide together, an incident is open, or the thread is going in circles.

---

## ⚠️ Anti-pattern

Task-switching, "just checking" chat, and meetings that do not need the room. Each one looks small. Together they spend the attention the hard task required.

---

## What focus is not

* A longer workday.
* A ban on collaboration.
* A private habit the rest of the team can ignore.
* A substitute for knowing the problem. The outcome of a block still comes from clarity.
