# 📖 Glossary: CRAFTER OS

| Term | System Definition | Principle |
|:---|:---|:---|
| **ADR (Architecture Decision Record)** | A document that captures a significant technical decision, its context, and its consequences. The "Black Box" of project evolution. | **C / A** |
| **Cognitive Clarity** | A state of 100% understanding of a task's logic and "Definition of Done" before writing code. | **C** |
| **First-principles thinking** | Breaking a task into the constraints that are actually true, rather than a pattern from the last project or a sample found online. | **C** |
| **Radical simplification** | If the logic cannot be explained in about two minutes, it is not understood yet. Map it before opening the editor. | **C** |
| **Definition of Done awareness** | The finish line, including invariants, edge cases, and quality gates, is agreed before the first line of code. | **C** |
| **Deep Work** | A 2-4 hour block of high-intensity focus with zero notifications or context switching. | **F** |
| **Single-tasking** | At most three active tasks. A new request joins that set only when something else pauses, and the people affected are told. | **F** |
| **Environmental control** | During a deep work block, ordinary chat, mail, and tabs stay quiet. Exceptions are named in advance, and the block is visible to the team. | **F** |
| **Signal-to-Noise** | The ratio of high-impact engineering work (code, architecture) to low-value friction (vague syncs, chat). | **C** |
| **Antifragility** | The property of a system or engineer to get stronger/better as a result of stressors and failures. | **A** |
| **Definition of Done** | A strict, non-negotiable checklist that must be met for a task to be considered complete (Tests, Docs, PR). | **E** |
| **Reputation Score** | A measure of reliability based on the delta between commitments made and results delivered. | **R** |
| **Broken Window** | A small bug, poorly written comment, or tech debt that degrades system quality. Must be fixed immediately. | **R** |
| **Analysis Paralysis** | A failure state where execution stops due to over-thinking. Solved via the "20-Min Mapping Rule". | **C** |
| **Low-level understanding** | Knowing the layer under an abstraction well enough to predict what the running system will do. | **T** |
| **Constant R&D** | About 10% of the working week spent on the How behind the What: question, research, experiment, evaluate, document. | **T** |
| **Architectural reasoning** | Judging a technical choice by its consequences, and recording a long-lived one as an ADR. | **T** |
